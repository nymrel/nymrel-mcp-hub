# Existing @Nymrel app: restricted JalenPC reads

The existing personal ChatGPT `@Nymrel` app is bound to `https://mcp.nymrel.com/mcp`. The hosted server now advertises four public studio utilities and seven OAuth-scoped Remote read tools. In the existing ChatGPT connection, the seven tool schemas are visible after Refresh, but Information still reports `Authorization supported: None` and `Authorization used: None`. A regular conversation reached a "ChatGPT needs more Nymrel access" prompt; it has not completed OAuth or read a local file. The backend plugin route remains disabled in production until the provider and exact subject map are validated.

## Logical resource and boundary

The hosted Nymrel MCP server is the **one OAuth resource** presented to ChatGPT:

```text
resource / access-token audience: https://mcp.nymrel.com/mcp
public ChatGPT app endpoint:      https://mcp.nymrel.com/mcp
Remote backend endpoint:          https://nymrel-remote-production.up.railway.app/nymrel/plugin/readonly/mcp
required scopes:                  devices:read tools:read
```

The hosted server must validate the caller's token and forward only the seven fixed read tools, with the original bearer token, to the backend endpoint. Remote independently verifies signature, exact issuer and audience, expiry, both read scopes, and the exact OAuth subject-to-tenant mapping. It discards any broader token scopes. The backend uses the same read-only broker and native device allowed-root boundary as `/chatgpt/readonly/mcp`, but records calls with `nymrel-plugin-readonly` provenance. `get_read_result` cannot retrieve calls created through a different profile.

The selected identity path is the bundled Nymrel OIDC issuer with a Google owner login. [Auth0 strict third-party applications](https://auth0.com/docs/get-started/applications/third-party-applications/security-controls) cannot supply the OIDC scopes ChatGPT requests from an OIDC-advertising authorization server; the prior Auth0 activation recipe has been withdrawn. The merged issuer source and disabled container smoke do not establish a live Google login, ChatGPT connection, or file read. See [issuer acceptance](../oidc-issuer/README.md) and [container gates](../oidc-issuer/CONTAINER.md).

Do not forward a `mcp.nymrel.com` audience token to `/chatgpt/readonly/mcp`. That route deliberately requires its own exact Railway URL audience. The backend route is disabled unless `NYMREL_REMOTE_NYMREL_PLUGIN_READONLY_ENABLED=true`; enabling it without an authorization server fails startup. Static compatibility tokens are never accepted there. No shared gateway bearer, model-visible token argument, or caller-selected tenant is part of this design.

## Activation sequence

Run `node scripts/check-nymrel-plugin-bridge.mjs` from `remote-control` before and after the identity cutover. It makes only anonymous requests. `backend_disabled` is the expected result while the protected production identity settings and bridge flag are absent. `ready_for_login_test` proves only public metadata, backend metadata, the two-scope anonymous challenge, and rejection of an invalid bearer; it deliberately reports `authenticatedChatgptRead: not_validated` until a real ordinary ChatGPT conversation reads an approved file. The live 2026-09-24 preflight found the backend route absent (HTTP 404) while Railway ran source commit `09aa7df`, which includes this route behind a disabled-by-default flag. Railway variable names confirmed the authorization server, issuer, subject mapping, and bridge flag were all unset; no secret values were printed.

1. Keep the dedicated `JalenPC-ChatGPTStudio` agent paired to `chatgpt-studio-20260922` and its reviewed staged root. Do not pair the original whole-profile JalenPC device to this tenant.
2. Treat the current **existing** ChatGPT `@Nymrel` connection as an authentication-none registration unless its management page exposes a real OAuth client configuration. The original app submission declared authentication `none`; its current management panel still has no editable callback/client and still reports `Authorization supported: None` after Refresh. Refresh reloads MCP metadata but is not evidence that a previously authless connection acquired an OAuth client. Do not keep refreshing it as a migration strategy.
3. Use an explicit new ChatGPT connection for the OAuth rollout when the existing connection has no client configuration surface. Point it at `https://mcp.nymrel.com/mcp`. Read the callback from that connection's management form; the stable `https://chatgpt.com/connector_platform_oauth_redirect` is supported only when the live client and issuer-identification flow accept it. Use a predefined public client with token-endpoint authentication `none`, authorization-code + PKCE S256, exact resource scopes `devices:read tools:read`, and the OIDC behavior requested by the actual ChatGPT form. Do not enable open DCR or relabel the OpenAI-operated client first-party to preserve the old connection.
4. Under a separate exact Google registration grant, register only the reviewed Nymrel Google Web client with callback `https://nymrel-remote-production.up.railway.app/google/callback`, Google `openid` only, and Jalen's owner account as the initial test audience. A Google client registration does not install production credentials or activate the issuer. Obtain separate scoped grants for private client/key custody and for the later issuer, gateway and Remote cutover. Keep the issuer's client definition bound to the logical plugin resource `https://mcp.nymrel.com/mcp`, both read scopes and the actual ChatGPT callback.
5. Prepare the issuer's private config and persistent SQLite volume under the separate custody grant. Keep the checked-in Railway enable flag `false` until activation. Require a runtime-owned private directory and config file, persistent keys, one issuer instance, and a tested backup/restore plan that invalidates old sessions. Offline issuer tests and a healthy disabled container do not prove a live login.
6. Under the separate activation grant, enable the issuer while the read bridge stays disabled. Publish and verify the new issuer in the hosted gateway's protected-resource metadata and pin the predefined ChatGPT client ID and actual callback there **before** the ChatGPT authorization test; the live gateway currently advertises Auth0. Keep the four public tools anonymous. Then complete a real Google login and ChatGPT authorization/cancel flow, checking PKCE S256, exact `resource`, requested OIDC/refresh scopes, state and issuer identification. Verify the resulting token privately against the Nymrel issuer's JWKS: RS256 signature, exact issuer, audience `https://mcp.nymrel.com/mcp`, both read scopes, expiry, and one stable internal `sub` mapped from the verified Google owner subject. A refresh token is acceptable only after a real refresh succeeds. The issuer currently releases `sub` but not `email` or `profile`; a ChatGPT request for unsupported scopes is a compatibility failure to resolve before bridge cutover.

   After that identity proof, set Remote `NYMREL_REMOTE_AUTHORIZATION_SERVERS` and exact `NYMREL_REMOTE_OAUTH_ISSUER` to the new issuer. Map only the verified internal `sub` to `chatgpt-studio-20260922` in `NYMREL_REMOTE_OAUTH_SUBJECT_TENANTS`. Enable `NYMREL_REMOTE_NYMREL_PLUGIN_READONLY_ENABLED` only after the verifier and hosted gateway are pinned to the same issuer and plugin audience. Update the checked-in Railway issuer flag as part of this reviewed cutover so a later apply does not silently disable it. Keep the direct read-only profile's audience unchanged. Missing or mismatched issuer, subject map, or authorization server must remain a startup failure. Prove one-instance volume recovery and private storage before treating the issuer as operational.
7. The hosted Nymrel adapter, exact plugin audience, per-tool OAuth security schemes, and `mcp/www_authenticate` challenges are deployed. Keep the four public studio tools anonymous and revalidate the live eleven-tool catalog plus protected-resource metadata after any provider change.
8. Perform the staged canary only after the backend is enabled: require exactly the isolated ChatGPTStudio device for the mapped tenant; read one pre-approved staged file and compare its expected SHA-256 without printing secrets; confirm a parent/credentials path is denied; exercise `nymrel_remote_get_read_result` for a pending read; then repeat an approved read after the original access token expires to prove refresh. Finally repeat the approved-read and denied-path checks from a new ordinary ChatGPT conversation. Do not claim regular ChatGPT local-file access before that conversation succeeds.

## Rollback

For immediate plugin closure, set `NYMREL_REMOTE_NYMREL_PLUGIN_READONLY_ENABLED=false` and disable the hosted adapter; this removes the backend route and preserves the direct read-only resource and public Nymrel tools. Turning off the issuer alone leaves already-issued access JWTs usable until expiry. If the subject itself must be revoked across all Remote routes, use a separate coordinated verifier change with a valid production map or intentionally stop the service: an empty subject map with an authorization server configured fails startup, and removing this identity also denies the direct resource. These controls do not change device pairing, allowed roots, or stored calls.

Local backend acceptance: `node --test test/chatgpt-readonly-http.test.js` covers disabled/default behavior, exact audience, static-token denial, mapped tenant isolation, frozen catalog, denied writes, and cross-profile pending-result isolation. These local tests do not prove the hosted adapter, live provider, ChatGPT sign-in, or production file read.
